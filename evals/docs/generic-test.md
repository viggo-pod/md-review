# 实时数据处理管道技术方案

## 概述

本文档描述订单数据实时处理管道的技术方案。管道从业务库采集订单数据，经过清洗、转换后写入数据仓库，供报表与推荐系统使用。本方案覆盖 ODS 层、DWD 层与 DWS 层。

## 1. 背景

随着业务增长，日均订单量从 2024 年的 1000 万增长到 2026 年的 1 亿。原有批处理方案已无法满足时效性要求，需要引入实时处理能力。

## 2. 架构设计

### 2.1 整体架构

业务库 → CDC 采集 → Kafka → Flink 处理 → 数据仓库

### 2.2 组件选型

| 组件 | 选型 | 版本 |
|---|---|---|
| 消息队列 | Kafka | 3.7 |
| 流处理 | Flink | 1.19 |
| 数据仓库 | Doris | 2.1 |
| 调度 | DolphinScheduler | 3.2 |

### 2.3 数据流向

1. CDC 组件采集业务库 binlog 变更
2. 变更数据写入 Kafka topic `ods_order`
3. Flink 任务消费 Kafka 并做清洗转换
4. 转换结果写入 Doris 表

### 3. 系统设计

## 4. 性能目标

| 指标 | 目标值 |
|---|---|
| 端到端延迟 | < 5 秒 |
| 吞吐量 | 1000 条/秒 |
| 数据保留 | 30 天 |
| 可用性 | 99.9% |

## 5. 容量规划

按照日订单 1 亿条估算，每秒平均处理约 1157 条。高峰期按 5 倍峰值估算，需要支撑 5800 条/秒的瞬时吞吐。Kafka 分区建议配置 32 个分区。原始数据保留 90 天以支持回溯分析。

## 6. 异常处理

- Kafka 消费失败自动重试，重试 3 次后进入死信队列
- Flink checkpoint 每 60 秒一次，故障时从最近 checkpoint 恢复
- 下游 Doris 写入失败时阻塞重试，避免数据丢失

## 7. 部署方案

采用 K8s 部署，Flink 任务与 Kafka 均为独立命名空间。监控使用 Prometheus + Grafana。

## 8. 验收标准

- 端到端延迟 P95 小于 5 秒
- 压测吞吐量达到 2000 条/秒
- 故障演练：Kafka 宕机 10 分钟可自动恢复
