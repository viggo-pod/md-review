# Intent Scenario Checklist — Product Intent Document

当场景参数为 `intent` 时启用。检查产品意图是否忠实表达问题、用户和可证伪的价值假设，而不是提前冻结技术方案。

## Core Questions

1. 目标用户和可观察问题是否清楚？
2. 证据、假设和未决问题是否明确区分？
3. 是否有足够信息支持声明的下一步决策，而没有越界成工程规格？

## Key Focus

问题与机会 + 用户 JTBD + 证据/假设 + MVP 与非目标

## Required Content — count-based scoring

### Problem and Users

- [ ] **Problem Statement**：是否说明特定用户、情境、问题和不解决的代价？
- [ ] **Current Alternatives**：是否说明用户当前如何应对以及现有替代方案？
- [ ] **Target Users**：是否定义角色、触发情境和非用户？
- [ ] **JTBD**：是否写出 When / Want / So that 的任务结构？

### Evidence and Hypothesis

- [ ] **Evidence Register**：每项事实是否有文件、URL、访谈或数据来源？
- [ ] **Fact vs Assumption**：事实、假设和推断是否显式区分？
- [ ] **Why Now and Differentiation**：是否说明时机及相对当前做法的差异？
- [ ] **Falsifiable Hypothesis**：是否同时写出 RIGHT 和 WRONG 条件及时间窗口？

### Scope and Decision Basis

- [ ] **MVP**：是否定义验证假设所需的最小端到端切片？
- [ ] **Non-goals**：是否明确不做什么？
- [ ] **Success Metrics**：是否有可测量指标、目标和测量方法？
- [ ] **Open Questions**：未决问题是否记录了影响和验证方法？
- [ ] **Decision Boundary**：是否清楚区分产品意图与解决方案、技术栈、数据模型或实现任务？

### 5W1H Check

- [ ] **Who**：谁有问题、谁受益、谁不是目标用户？
- [ ] **What**：要解决什么问题、产生什么结果？
- [ ] **Why**：为什么值得做、为什么现在做？
- [ ] **When**：何时触发问题和验证？
- [ ] **Where**：在哪个场景、渠道或工作流中发生？
- [ ] **How**：如何用 MVP 验证，而不是如何实现系统？

## Completeness Issue Markers

- 把解决方案当作问题陈述
- 用“用户想要”替代证据
- 没有 WRONG 条件或没有非目标
- 在意图文档中冻结技术实现
